# Key Workflows

This document walks through concrete end-to-end workflows that SignalKit supports today, and identifies workflows that users would naturally expect but aren't yet implemented.

## Supported workflows

### 1. Weekly prospecting pipeline (fully automated)

**Trigger:** The cron job fires every Monday at 06:00 UTC.

**Flow:**
1. Cron enqueues `collect:yc_directory` and `evaluate_triggers:fanout`.
2. Worker collects fresh company data from the YC API. New companies are inserted; existing ones are updated.
3. For each company with a website, worker enqueues `enrich` (homepage) and `detect:hosting`.
4. Homepage enricher scrapes the page, discovers careers/login links, enqueues sub-page enrichment.
5. Each enricher persists content and (if content changed) triggers AI detection.
6. Website analysis detector sends page text to Claude, extracting `careers_page`, `product_profile`, and `tech_stack` signals.
7. Hosting detector runs DNS/HTTP checks, writes `hosting_detected` signals.
8. Trigger evaluation runs per-company. Any matching rules fire actions.
9. Actions (prospect brief, outreach draft, cost analysis, change alert) are generated by Claude and stored.
10. Deliveries persist to the dashboard (and optionally Slack/webhook).

**User experience:** Check the dashboard on Monday afternoon and find fresh prospect briefs and outreach drafts waiting. No manual intervention after initial setup.

### 2. Manual single-company sync

**Trigger:** User clicks "Sync" on a company detail page in the dashboard.

**Flow:**
1. Web API enqueues `enrich` (homepage) and `detect:hosting` for that company.
2. Worker runs enrichment, detection, trigger evaluation, and any resulting actions.
3. User refreshes the company detail page to see updated signals and action output.

**Use case:** You just added a company manually or want fresh data before a sales call.

### 3. Manual collection run from the Sources page

**Trigger:** User clicks "Run" next to a data source on the Sources page.

**Flow:**
1. Web API enqueues the collection job (e.g. `collect:yc_directory`).
2. Worker runs the full collection pipeline: fetch companies, upsert, enqueue enrichment and hosting detection for each.

**Use case:** Don't want to wait for Monday. Pull fresh data now.

### 4. Trigger-based alert on hosting change

**Setup:** User creates a trigger:
- Condition: `hosting_detected` exists AND `hosting_detected.provider` equals `heroku`
- Action: `change_alert`
- Delivery: `dashboard` (or `slack` with a webhook URL)

**Flow:** When a company's hosting is detected as Heroku, the trigger fires. Claude generates a change alert describing what was detected. If Slack delivery is configured, a message posts to your channel.

**Use case:** Get notified when a prospect is on a competitor's platform.

### 5. Conditional outreach based on signal combination

**Setup:** User creates a trigger:
- Match: `all`
- Conditions:
  - `hosting_detected` field `provider` equals `heroku`
  - `careers_page` exists
- Action: `outreach_draft`
- Delivery: `dashboard`

**Flow:** When a company is on Heroku AND has a careers page (suggesting active hiring/growth), Claude writes a personalized outreach email referencing both signals.

**Use case:** Only draft outreach when the prospect matches a specific ICP (infrastructure + growth signals together).

### 6. Cost comparison for prospects

**Setup:** Trigger with condition `hosting_detected` exists, action `cost_analysis`.

**Flow:** For any company with a detected hosting provider, Claude generates a cost comparison (current vs. alternative provider), including assumptions and a recommendation.

**Use case:** Arm your sales team with a specific cost argument before outreach.

### 7. Slack notification on new prospect brief

**Setup:** Trigger with action `prospect_brief`, delivery `slack` with config `{ "webhookUrl": "https://hooks.slack.com/...", "username": "SignalKit" }`.

**Flow:** When a prospect brief is generated, the Slack delivery sends a formatted summary to your channel with the company name and headline.

**Use case:** Team-wide visibility into new prospects without checking the dashboard.

### 8. Webhook delivery to external systems

**Setup:** Trigger with delivery `webhook` and config `{ "url": "https://your-crm.com/api/signals", "headers": { "Authorization": "Bearer ..." } }`.

**Flow:** When an action completes, the webhook delivery POSTs the full output (action type, company info, AI-generated content) to your endpoint.

**Use case:** Push SignalKit intelligence into Salesforce, HubSpot, or a custom CRM.

### 2. Run the pipeline on demand for a specific company list

**What users expect:** Select 10 companies from the dashboard and click "Analyze these now."

**Current gap:** Sync works per-company only. There's no bulk-select UI or batch-sync API endpoint.

**What it would take:**
- A `POST /api/sync` endpoint that accepts an array of company IDs and enqueues enrichment + detection for each.
- A multi-select UI on the Companies page with a "Sync selected" action.


### 3. Edit or re-run a specific action

**What users expect:** View a prospect brief, decide it's not quite right, and click "Regenerate" — possibly with a modified prompt or additional context.

**Current gap:** Actions are write-once. The only way to regenerate is to delete the action run from the DB and let the trigger fire again (which requires a signal hash change) or create a new trigger.

**What it would take:**
- A "Re-run" button on the action detail page that creates a new action run for the same company + signals.
- Optionally, an "Edit prompt" UI that lets you tweak the prompt template before regeneration.

### 5. Trigger conditions based on company metadata (not just signals)

**What users expect:** "Only generate outreach for companies with team_size < 30" or "Skip companies in batch W25."

**Current gap:** Trigger conditions only evaluate against the `signals` table (signal_type + field within signal value). Company metadata (team_size, batch, industry) isn't accessible in trigger conditions.

**What it would take:**
- Extend `TriggerCondition` to support a `source: 'company'` field type.
- Update `evaluateCondition` to pull from company metadata in addition to signals.
- Update the trigger form UI to expose company fields as condition sources.

### 8. Dashboard filtering by signal state

**What users expect:** "Show me all companies on Heroku with > 20 employees" as a saved view/filter.

**Current gap:** The Companies page lists all companies. Filtering by signal values requires custom SQL queries — the UI doesn't support signal-based filtering or saved views.

**What it would take:**
- A filter UI on the Companies page that queries joined company + signals data.

### 9. Unsubscribe / exclude a company

**What users expect:** "Stop monitoring this company" or "Exclude this company from all triggers."

**Current gap:** All companies in the DB are included in every trigger fanout. There's no exclusion or archive mechanism.

**What it would take:**
- An `isArchived` or `excludedFromTriggers` flag on the company.
- Fanout and trigger evaluation skip archived companies.
- A UI toggle on the company detail page.


### 7. Multi-step action chains

**What users expect:** "First generate a prospect brief, then use that brief to write an outreach email" — where the second action's prompt references the first action's output.

**Current gap:** Actions are independent. An `outreach_draft` action takes company + raw signals as input; it can't reference a previously generated `prospect_brief`. Each action starts from scratch.

**What it would take:**
- An action chain mechanism where a trigger can specify ordered actions with output-forwarding.
- Or: make previous action outputs available in `PipelineContext` so later actions can reference them.

## Persona (who it's for)

### Target persona: GTM Engineer

**What is a GTM Engineer?**
- Hybrid role — half commercial thinker, half builder. Clay's characterization: "marketers who are bad engineers" or "engineers who care more about moving revenue than writing perfect code"
- They own the technical systems that make revenue teams run: data pipelines, enrichment workflows, signal detection, outreach automation
- Distinct from RevOps (strategy/process) and SDRs (execution). GTM Engineers are the **architects** — they build the systems both depend on
- Role coined by Clay in 2023, now hired at OpenAI, Ramp, Vercel, Anthropic, Cursor, Webflow
- 205% YoY job growth, 3,000+ open positions, $132K–$300K+ comp range

**Where they come from**
- Sales/Marketing Ops who hit the ceiling of what they could build with existing tools (most common path)
- SDR/BDRs with a technical lean who got frustrated with clunky tools and started building better ones
- Data analysts in revenue functions who already have SQL/Python and learn the tooling ecosystem
- Software engineers moving toward GTM (less common but companies pay premiums for this profile)

**Technical profile**
- Core fluency: APIs, webhooks, prompt engineering, data modeling, CRM architecture
- SQL and Python each appear in 38% of job postings; cold calling in only 1.4% — this is not an SDR rebrand
- Most work done with no-code/low-code, but roles requiring code pay ~$40–45K more
- AI skills command a 15–25% premium; ~70% already use AI-native dev tools (Cursor, Claude Code)
- The role is splitting into two tracks: low-code operators ($60–90K) vs. high-code engineers ($135K+)

**Psychographic profile — what makes them tick**
- **Builder mentality** — they hack on projects nights and weekends, learn by building
- **AI-native** — not casual ChatGPT users; deploying agents, understanding prompting deeply, building with LLMs daily
- **Commercial bias** — always asking "does this workflow actually help close a deal?"
- **Systems thinkers** — they see the full revenue lifecycle, not just one channel
- **IC-track** — want to stay individual contributors who ship, similar to principal engineers in software

**Their current stack (and where SignalKit fits)**
- Enrichment & orchestration: Clay (84% adoption), Apollo, ZoomInfo
- CRM: Salesforce/HubSpot (~88% combined)
- Outreach: Instantly, Smartlead, Outreach
- Automation middleware: n8n, Make, Zapier
- AI/LLMs: Claude, GPT, Cursor
- Scripting: Python, JS, SQL — "for when no-code hits a wall"
- **SignalKit lives in the gap between enrichment and outreach** — the signal detection, trigger evaluation, and AI-generated action layer that most teams cobble together from 4–5 disconnected tools

**Why SignalKit resonates with this persona**
- They **build exactly this type of system** manually today — Clay tables, enrichment waterfalls, custom scripts to detect signals, prompt templates for outreach drafts. SignalKit is a complete reference architecture for this workflow
- It's **code they can read, fork, and extend** — not a black-box SaaS. The plugin system (defineCollector, defineDetector, defineAction) matches how they think: composable, extensible building blocks
- It runs on **infrastructure they understand** — TypeScript, Postgres, Redis, BullMQ. No exotic runtime. One `render.yaml` deploys the whole stack
- It demonstrates **AI integration patterns they need** — structured outputs with Zod schemas, prompt templating, LLM observability with token/latency tracking. These are the exact patterns they're implementing at work
- The **"SDR economics broke" macro trend** is the core pitch — one GTM Engineer + automation replaces multiple SDR headcount. SignalKit is a working example of that thesis: automated collection → enrichment → AI detection → personalized outreach, hands-free on a weekly schedule
- Stack consolidation trend: teams moving from 15+ tools to fewer integrated platforms. SignalKit shows how to collapse the enrichment → detection → action → delivery chain into one deployable system
